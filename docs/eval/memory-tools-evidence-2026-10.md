# Memory / code-graph tool evidence, and what it means for how we read the atlas results

Status: research note by an agent, 2026-10-22. Not registered, not scored, no decision. It extends `docs/eval/reevaluation-options.md` section 3 (not repeated here) and reads, without editing, `analysis.md`, `diagnosis.md`, `angular-pilot/v2/pilot-results.md`, `pilot-audit.md`, `gate-redefinition-proposal.md` and `README.md`. All web sources accessed 2026-10-22. "Fetched" = I read the primary page through the fetch tool, whose answers come from a small summarising model (numbers are as it returned them). "Search only" = seen in a search-result summary, primary not read. "Vendor claim" = number produced by the party selling or authoring the tool.

## Summary

1. The big token-saving numbers (57-99%) come from vendor harnesses whose baseline is an open-ended, single-question exploration that costs the no-tool agent 6-43 tool calls and 0-18 file reads. Our grep arm averages 3.5 calls (gsd-core) and 5.1 calls (Angular pilot). The tools are measured against a much more expensive baseline than ours; direction of our result is not odd, the baseline is.
2. Where the baseline is cheap, independent-ish results agree with us: tool authors' own controlled runs (nefayran, samchon) and a preliminary single-author study (arXiv 2608.13568) find graph/LSP tools equal or dearer than Read/Grep on tokens, with graph tools mainly helping accuracy on structural questions.
3. Our "billable tokens" sums cache reads at weight 1. Current pricing weights them 0.05 (Sonnet 5.5) to 0.1. Re-weighting our own pilot rows reproduces the logged cost and gives A-reg/G = 1.52 (not 2.25) and A-ts/G = 1.10 (not 1.22); registered run 1.19 (not 1.61). The sign does not flip.
4. The only graph tool with a published harness that I read (CodeGraph) is one tool that returns verbatim source plus call paths, so the agent makes 0 file reads. Atlas returns cited locations; a preliminary study finds location-only results force follow-up reads (+19% tokens). Atlas calls displaced 38 shell calls for 93 atlas calls (`diagnosis.md` section 2). This is the best-supported feature gap.
5. Adoption is a delivery problem everywhere: deferral gave 2/12 tool use (nefayran) and 2/32 (our A-ts); Vercel found a skill was never invoked in 56% of cases while a passive injected index scored 100% against 53% baseline. Claude Code defers MCP tools by default; our harness did not (omitted ToolSearch), which is why registered and pilot A-reg overheads are not what a default user pays.
6. "Memory" (decision memory, cross-session notes) is not what any token benchmark I found measures. The one controlled study of repository context files finds generated ones cut success slightly and raise cost over 20%.
7. No evidence found that single-question sessions are an unrepresentative test; the vendors use them too. No evidence found on multi-question amortisation either way. That is untested, not refuted.
8. Evidence supports a narrower reason to exist: cited, exact structural facts and post-cutoff platform facts as accuracy aids; it weakens "saves tokens on name-addressable questions".
9. SDK half: grounding on post-cutoff APIs helps strongly in the one clean study (Vercel, Next.js 16: 53% to 100%) and partly in a 270-update study (42.6% to 66.4% executable); nothing Apple-specific was found; our eval does not touch it.
10. Several of these claims are checkable against data we already hold (section 6, items 1-2) before spending on new runs.

## 2. Q1 and Q2: what the savings numbers actually measure

**What differs between their metric and ours.**

| Dimension | Vendor harnesses (CodeGraph, codebase-memory) | Ours |
|---|---|---|
| Question type | Open-ended "how does X work" prose answer, no key, no accuracy | Enumeration with exact-set keys from a compiler oracle |
| Baseline length | 6-43 tool calls, 0-18 file reads per session (CodeGraph); explorer 4.8 calls (paper) | 3.5 calls (gsd-core), 5.1 (Angular G) |
| Token convention | Total per-turn input incl. cache reads (CodeGraph); unspecified (paper); chars/4 of one response (Memtrace) | Sum of input + output + cache creation + cache read, cache read at weight 1 (`analysis.md`, D-06) |
| Cost | CodeGraph also reports `total_cost_usd`; savings shrink (Django 13%, Gin ~0) | Priced cost reported (1.19 registered, 1.51 pilot A-reg) |
| Tool shape | 1 tool (`codegraph_explore`), returns verbatim source + call paths, usage instructions in MCP `initialize`, installer writes a CLAUDE.md section, `alwaysLoad` suggested | 7 tools, locations/citations; deferral off by harness |
| Quality | Not measured (CodeGraph); lower than baseline (codebase-memory, 0.83 vs 0.92) | Primary |
| Who ran it | Tool author | Tool author, but pre-registered with a replication |

**Is our interpretation the odd one out?** Partly. The unit (billable tokens, single question) is the same one CodeGraph and nefayran use; what is odd is that our baseline is cheap and our metric is unweighted. Three separate effects, each checkable:

1. Baseline cost. CodeGraph's own table shows the saving tracks how many calls the baseline needs: 57-78% savings at 28-43 baseline calls, 13% at 14 calls (Django), ~0 at 7 calls (Gin). Our G sessions are at the Gin end (3.5-5 calls). On this evidence a null or negative token result on name-addressable questions is what the vendors' own table predicts.
2. Cache weighting. Prompt-caching docs (fetched): cache write 1.25x, cache read 0.1x base input, and 0.05x for Claude Sonnet 5.5. Our sums weight cache read at 1. Using the pilot's logged means (output weighted at 5x input: an assumption, not verified for this model; the check is that the result reproduces the logged cost):

   | arm | weighted units | ratio to G | logged cost ratio | unweighted token ratio (`pilot-results.md`) |
   |---|---:|---:|---:|---:|
   | G | 27,028 | 1.00 | 1.00 | 1.00 |
   | A-ts | 29,820 | 1.10 | 1.10 (2.526/2.287) | 1.22 |
   | A-reg | 40,984 | 1.52 | 1.51 (3.453/2.287) | 2.25 |

   Registered run: atlas 14,127 vs grep 11,892 = 1.19, matching `analysis.md` cost 1.19 (token ratio 1.61). The re-weighting does not rescue the token claim, but it shows the pilot's 2.25 is a measurement convention as much as a cost: in priced terms the excess is cache creation and output (fresh tokens), not the cached tool definitions. Note A-reg's priced ratio (1.51) sits on the proposed R_max of 1.5; that is descriptive and must not be used to tune it (`gate-redefinition-proposal.md` section 5).
3. Tool shape and delivery (section 4).

**Tool-definition overhead, deferral, skills versus MCP.**
- Claude Code docs (fetched): tool search is on by default, only tool names and server instructions load at session start, and "If you deny `ToolSearch` or leave it out of `--tools`, MCP tools load upfront instead". The atlas harness used `--tools Bash,Read` (per `reevaluation-options.md` A.1); that explains why definitions were upfront and is a harness artefact rather than a default-user cost. Extension, not contradiction, of A.1. Auto threshold: defer once definitions reach 10% of context (`ENABLE_TOOL_SEARCH=auto:N`). Server authors get `anthropic/alwaysLoad` per tool (v2.1.285+) and the user's setting can override it; tool-description limit when deferred is 16,384 characters, shorter when upfront (v2.1.296 changed the limit from 2,048 characters).
- Anthropic (fetched): 77K to 8.7K tokens and accuracy 49%->74% (Opus 4), 79.5%->88.1% (Opus 4.5) on unnamed internal MCP evals for large libraries. Vendor claim; atlas's 7 tools are far below that regime. Memtrace, CodeGraph and Serena each respond differently: CodeGraph ships one tool and `alwaysLoad`; this very session lists dozens of Memtrace tools, all deferred.
- Adoption under deferral: nefayran 2/12 runs called the graph; our A-ts 2/32. With a CLAUDE.md-style routing rule or always-load, adoption rose in nefayran's study (exact rate not given in what I read). Vercel: default skill never invoked in 56% of cases. arXiv 2608.13568: 0% free-choice semantic use on Opus 4.8.
- Skills vs MCP vs CLI: only vendor posts (Scalekit, Smithery, via search) and an unverified `mcp-vs-cli-bench`; they attribute the gap to schema size on simple tasks. No independent measurement of skill progressive disclosure found.

## 4. Q4: where structural graph tools win, and the single-question issue

- Wins reported: large repos with exploratory questions (VS Code, Excalidraw, Tokio, Alamofire in CodeGraph's table: 57-78%); structural questions for the weakest model (nefayran: Haiku on dub 12/12 vs 8/12; 2608.13568: Haiku -26%, precision 1.00 vs 0.76 on references); hub detection and caller ranking (codebase-memory paper, 19 of 31 languages). Loses or ties: small repos, name-addressed lookups, exhaustive call-site enumeration where grep recall is higher, macro-heavy C, renames (grep pass 1.00 vs location-only LSP 0.67).
- Language/size: CodeGraph's strongest results are on TS (11k and 640 files), Rust, Swift; weakest on Go (110 files) and Python 3k files. The Angular pilot (11.6k files, TS) is in the winning regime on size yet G averaged only 5.1 calls, because the questions name a symbol. That suggests question type, not repo size, drives it (consistent with `reevaluation-options.md` 2.5).
- Caching: definitions and context are cached, so repeated turns re-read them at 0.05-0.1x. A longer session pays the fixed block each turn at the discounted price, and a graph tool that removes turns removes whole-context re-reads. This is why CodeGraph's gain scales with baseline turns. CodeGraph states the opposite cost: ~80% more retrieval context left resident (67k vs 18k on VS Code), a cost against the window in long sessions, not billed tokens.
- Are single-question sessions unrepresentative? I found no study that says so. The vendors' headline numbers are also single-question sessions, and 2608.13568 is single-task. What is missing everywhere is multi-question amortisation (does the second question in a session get cheaper because the first one's index/context persists?). Real agent work is multi-turn editing, and the benefit of reusing a graph across many lookups is plausible but unmeasured. I would not call our design unrepresentative on this evidence; I would call it silent on amortisation.
- SDK/platform half: no Apple-specific study found. Related: arXiv 2406.09834 (Python deprecated APIs, 25-37% deprecated usage, prior note); arXiv 2604.09515 (270 API updates, 8 Python libraries, 11 models: ~42.6% of generated examples executable without documentation, ~66.4% with structured documentation, reasoning +11%, "outdated patterns persist even when updated specifications are provided"); Vercel (post-cutoff Next.js 16 APIs: baseline 53%, injected docs index 100%, skill invoked only on request 53-79%); APILOT "89.42% fewer outdated recommendations" (abstract claim, search only, Python). Together: grounding helps, helps most when injected rather than offered, does not fully fix the problem. Nothing measures agents asserting OS availability (introduced/deprecated versions) for Apple APIs; that remains an argument, not a result.

## 5. Q5: implications (falsifiable; the owner decides)

Checkable now on data we hold (no new sessions):
1. Replace "billable tokens" with the priced ratio as the headline (the weights above reproduce logged cost to within 0.01). Prediction: recomputing from `pilot-sessions.jsonl` per question reproduces 1.10 / 1.52; falsified if per-question reweighted ratios diverge from logged cost.
2. Test the baseline-hardness hypothesis: regress A-reg/G (and A-ts/G) on G's tool-call count across the 16 pilot questions, and on gsd-core's 75. Prediction from CodeGraph's table: ratio falls as G calls rise; falsified if flat. A pre-registered threshold ("savings claimed only where G >= N calls") would follow.
3. Count shell calls displaced per atlas call and bytes of atlas results per call by tool; confirm whether results carry source bodies (item 1 of section 3).

Needs new, small, unscored probes:
4. Run atlas under CodeGraph's published harness (one architecture question per repo, `claude -p --strict-mcp-config`, 4 runs, median, same repos) for a like-for-like number. Prediction: atlas shows large savings only on baselines of 20+ calls; falsified if atlas is dearer even there.
5. One-tool, source-returning variant of atlas (or a `code_context`-style call returning bounded source + callers) versus the seven location tools on the same 16 pilot questions. Prediction (2608.13568): ~19% fewer tokens and fewer reads; falsified if reads do not fall.
6. Delivery arms: `alwaysLoad`/ToolSearch left in `--tools` (default user), server `instructions`, a fenced CLAUDE.md block, and a hook-injected hint. Prediction (Vercel, nefayran): N4 adoption >= 0.5 only with passive text; falsified if adoption stays near 6% with passive text.
7. A passive-index control arm: a short directory/symbol map in context with no tool. Separates "information" from "tool-call mechanism"; AGENTS.md paper predicts no gain and +20% cost.
8. A multi-question session arm (e.g. five related questions per session): test whether per-question cost falls with question index. Falsified if flat.
9. Include one SDK-fact stratum (post-cutoff Apple API availability) with the grep arm unable to answer from repo text; predict the Vercel-sized gap only if facts are injected or the tool is called.

Does the evidence support the project's reason to exist? Honest reading: it supports a narrower one. (a) Weakened: the claim that a structural map reduces tokens or cost on name-addressable questions in cheap-to-grep corpora; three tool-author-run controlled comparisons (nefayran, samchon, 2608.13568) found equal or higher cost, and the strongest savings need exploration-heavy baselines atlas has not been tested on. (b) Not contradicted but not shown: accuracy gains on hard structural questions (84% vs 72%, not significant, and called sessions were less accurate than non-called; external parallels are small: nefayran 12/12 vs 8/12, 2608.13568 precision). (c) Supported in principle, untested by us: grounded, current platform facts, since the adjacent evidence (Vercel, 2604.09515) shows models lack post-cutoff API knowledge and that injected facts help. (d) The "memory" tools' headline advantages (decision memory, history, fleet coordination) do not appear in any token benchmark I found, so they are not evidence for or against atlas's measured result.

## 6. Contradictions with `reevaluation-options.md` section 3, and updates

- 3.1 said no published controlled study compares graph tools with grep. Now two exist, both by tool authors: arXiv 2603.27277 (graph quality 0.83 vs explorer 0.92) and nefayran's repo; one third-party measurement (samchon). They agree with our direction on tokens for cheap baselines. The note's own condition ("a published, controlled study ... should replace sections 3.1 and 3.2") is only partly met.
- S6 (CodeGraph "seen in search only, 23-64% savings") is now fetched at the README: the 57%/62% figures use one question per repo, no accuracy metric, and the savings vary from 78% to ~0 with baseline length.
- A.1 (no deferral in the harness) is consistent with the docs: omitting ToolSearch from `--tools` forces upfront loading. Default Claude Code defers, so A-ts is the default-user condition and A-reg approximates `alwaysLoad`.
- 3.3 said I could not read the deferral thresholds; they are now read: `auto` = defer when definitions reach 10% of context; tool search default-on for Opus 4/Sonnet 4/Haiku 4.5 and later; MCP output warning at 10,000 tokens, text results over 50,000 characters spill to disk unless the tool declares `anthropic/maxResultSizeChars`.
- 3.4: "first-party numbers on grep-only agentic search cost were not found" still holds. Anthropic's tool-search numbers are about definition loading, not search.

## 7. Limits and what I could not verify

- Fetch answers were produced by a summarising model; figures were not re-checked against raw text except where a table was quoted. Many third-party figures (Graft, Zilliz, Mem0 headline, Scalekit/Smithery, Memtrace "3.2x") are search-only and unverified at the primary.
- arXiv 2608.13568: the fetched HTML did not state a submission date; the earlier note recorded an inconsistency (identifier prefix vs "29 June 2026"). I did not resolve it. The paper's TS repositories are not strictly typed, repo-map arm untested, tasks ~1k tokens.
- codebase-memory paper: token counting method not stated; first-author grading; total question count not stated.
- samchon article: year not shown; token types, run counts, model list incomplete; the winning tool is the author's.
- nefayran: page undated; author built the wrapper; an earlier private-repo round that showed savings "did not reproduce" (per the page).
- Memtrace: I read the benchmark README, not an agent-level run (none exists per its own page). I did not run Memtrace, CodeGraph, Serena or any tool; I did not inspect atlas's source for output shape.
- The 1.52/1.10 re-weighting assumes output priced at 5x input and 5-minute cache writes; the check is agreement with logged cost (within 0.01), not a price list for the model. The 0.05x Sonnet 5.5 cache-read multiplier is from the prompt-caching page (only the first 100,000 of 160,080 characters read).
- No Apple-specific study of OS-availability hallucination was found; absence of evidence here is from search, not from an exhaustive review.
- Independent replication of any vendor number was not found. "Independent-ish" above means a different author from the tool's vendor; in two cases the author wrote the competing tool.
- Skills-vs-MCP and MCP-vs-CLI overhead evidence is vendor or self-reported; `mcp-vs-cli-bench` itself was not located.
