# Free alternatives to gsd-atlas

Status: Final

Evaluated before the eval is designed (EVL-01, decision D-05). This is a scan, not a benchmark: it records what each tool answers well and where it stops, on the same eight gsd-core questions with the same model, and it produces no ranking. It is not an eval arm. The questions are in [scan-questions.md](scan-questions.md); the per-session numbers are in `scan-runs/`.

Commit pinned for every live run: gsd-core `10ac3a7a947903ba50f538a907af036744d759d5` (`corpora/corpora.json`). Desk claims below carry their source and the date read (2026-10-18); a live run confirms or contradicts them where one exists.

One result needs stating before the table. In the 32 live sessions of the four tools installed for this scan, the model never called a tool of the tool under test: every session answered from shell search alone (`git grep`, `grep`, `cat`), and all four reached the same marking (7 yes, 1 partial). Those four live runs therefore show what each tool costs to carry in a session and what the model did when offered it, not what the tool would have answered. The statements about what each tool cannot do come from the desk review and from a few direct, non-model probes made on the same checkout, and each is labelled as such.

## Method

- **Questions.** The same eight gsd-core questions, [scan-questions.md](scan-questions.md), asked once per tool in the order s-001 to s-008. They were drafted from gsd-core source and ADRs without any code-intelligence tool, they are disjoint from the scored eval set, and each carries an answer key computed by the independent oracle of plan 03-04.
- **Model.** The same model alias for every tool (`sonnet`); each run file records the model id the program reported (`claude-sonnet-5-5`) and the Claude Code version (2.1.302).
- **Isolation.** Headless `claude -p` with `--setting-sources ""` (no user, project or local settings, so none of this machine's own code-intelligence guards or servers load), `--strict-mcp-config` naming only the tool under test, no other plugin, `--tools Bash,Read` (plus `LSP` for the plugin row), and read-only shell patterns allowed (`git grep`, `git ls-files`, `rg`, `grep`, `ls`, `cat`, `head`, `tail`, `wc`). Every tool gets exactly these plus its own tools; the init event of each session is recorded, including the tool list and the MCP server status.
- **Checkout.** A throwaway checkout of the pinned commit, outside the repository, one copy per tool. Nothing here ran against a checkout the user works in.
- **Tool set-up.** One run per tool with the configuration its documentation names for Claude Code, and nothing tuned to the questions: mcp-language-server started with the workspace and `typescript-language-server --stdio`; Serena with `--context claude-code` and the project path, dashboard off, and its default REPL interface; the Aider repo-map generated with `--show-repo-map` and placed verbatim in the prompt of every session; the LSP plugin through a local plugin directory. Serena was given a project file and a symbol index before the sessions (14 s).
- **Budget.** The approved `scan.maxBudgetUsdPerSession` (3 USD) and `scan.sessionWallClockMs` (900000 ms) from the approved constants file apply to every session; a session that reaches either is recorded as such and not retried. No session reached either. The committed runs total 40 sessions (8 for codegraph plus 32 for the four installed tools), at 2.46 USD.
- **Answer and marking.** The final message ends with one JSON block of `{file, line?, symbol?}` items or an abstention. Marking is file-level against the oracle's key: `yes` (every key file and nothing else), `partial` (some), `no` (none, no parseable answer, or an answer where the key abstains). This is a scan-only check, not the eval scorer.
- **What is recorded.** Per session: status, marking, the four token fields and their sum, tool calls by name, wall time, cost, the init tool list and a short gap note. No transcript and no repository text is committed.
- **What is not claimed.** One run per question; model output varies, so a rerun need not match. The numbers say what happened in one session, not which tool is better. Because the model chose shell search in every session of the four installed tools, the equal markings say that shell search sufficed for these eight questions, not that the tools matched one another. The probes are single calls, not repeated measurements.

## Desk review

Sources are named with the date read (2026-10-18). Claims marked Observed come from the live run or the tool's own CLI on the throwaway checkout; claims marked Probe come from a direct call to the tool with no model; claims marked Desk come from the source.

### mcp-language-server and Serena

- mcp-language-server (isaacphi, Go, BSD-style license): "runs and exposes a language server to LLMs"; tools `definition`, `references`, `diagnostics`, `hover`, `rename_symbol`, `edit_file`; setup is `go install` of the module plus a language server and a client entry with `--workspace` and `--lsp`; the README calls it beta software; GitHub shows release v0.1.1 on 2025-05-16 and the last commit on 2025-06-03. Source: https://github.com/isaacphi/mcp-language-server (README, releases, commits via the public API). Observed: the binary installed from v0.1.1 identifies itself as v0.0.2 in the MCP handshake. Probe: with the TypeScript server and this checkout, `definition` and `references` take only a symbol name and went through the server's workspace symbol search, which failed with "No Project" until a file had been opened and then reported "not found"; the checkout has only `.cts`, `.cjs` and `.js` files, so the cause may be the file extensions or the project setup, and it was not isolated.
- Serena (oraios): symbol-level retrieval, editing and refactoring over MCP; language-server backend by default (40+ languages) or a paid JetBrains plugin; retrieval tools find symbol, symbol overview, find referencing symbols; type hierarchy and some refactorings are JetBrains-only; find implementations is "limited by the language server"; "agent-first tool design" that avoids "low-level concepts like line numbers"; installed with `uv tool install -p 3.13 serena-agent`, license GPL-3.0-or-later for the application and MIT for SolidLSP; user data in `~/.serena` unless `SERENA_HOME` is set; the README warns against installing through an MCP or plugin marketplace. Sources: https://github.com/oraios/serena, https://oraios.github.io/serena/02-usage/050_configuration.html, https://pypi.org/project/serena-agent/ (2.0.0, requires Python 3.11 to 3.14). Observed: its generated configuration defaults to the REPL agent interface, so a Claude Code session sees two tools. Probe with the one-tool-per-operation interface: `find_symbol` returned the `.cts` function and same-named local bindings in `.cjs` files with line numbers; `find_referencing_symbols` for the `.cts` function listed two `.cts` files and no `.cjs` or `.js` file.

### Aider repo-map

- A concise map of the git repository listing "the most important classes and functions along with their types and call signatures", sent to the model with each request; files are graph nodes with dependency edges, ranked to fit a token budget set by `--map-tokens` (1k by default, expanded when no files are in the chat; 4,096 tokens in this run); `--show-repo-map` prints it. It supplies orientation, not answers to caller or implementer questions. Sources: https://aider.chat/docs/repomap.html, https://aider.chat/docs/config/options.html, https://pypi.org/project/aider-chat/ (0.86.2, requires Python 3.10 to 3.12). Observed: the map printed for the checkout names 21 files, mostly hook and editor-plugin scripts, and no `.cts` file; it needs `--no-gitignore` to run without writing to the repository and without a prompt.

### colbymchenry/codegraph

- MIT-licensed local code graph: a SQLite database of symbols and edges, parsed by a native kernel for 20 languages, served over MCP as `codegraph_explore` (`codegraph serve --mcp`), kept fresh by a file watcher, stated as "100% local" with a separate opt-out anonymous usage telemetry. Source: https://github.com/colbymchenry/codegraph (README), `codegraph --help` and `codegraph telemetry status` on 1.6.2.
- Observed on the pinned checkout: see the table row and `scan-runs/codegraph.json`. The tool's own `callers` command for the function in s-001 reports two definitions with only `.cts` callers; an `explore` query "which files cite ADR-58" returns symbols from `scripts/gen-adr-index.cjs` and `src/adr-parser.cts`, not the citing files. While reading, a result headed "from a different git worktree" appeared when the CLI was run in a linked worktree without its own index.

### Claude Code LSP plugin

- Code intelligence plugins connect Claude Code to a language server over LSP; the plugin "doesn't include the language server", only the command and file extensions; the official `typescript-lsp` plugin needs `typescript-language-server`; a language without an official plugin is connected by a plugin with an `.lsp.json`, loaded with `--plugin-dir`. Sources: https://code.claude.com/docs/en/plugins/code-intelligence, https://code.claude.com/docs/en/plugins-reference (LSP servers fields: `command`, `args`, `extensionToLanguage`, `startupTimeout`, `requestTimeout`, `restartOnCrash`). Observed: with a local `.lsp.json` mapping `.ts`, `.cts`, `.mts`, `.js`, `.cjs` and `.mjs`, the headless session's init event listed the `LSP` tool.

### Memtrace

- Desk-only. Paid; its monthly quota is exhausted, so nothing was installed or called. The capability list and the worktree caveat in the table come from the text of this machine's CodeGraph-first routing guard, which names the Memtrace tools and says that only `find_code` accepts a `worktree` argument. No Memtrace documentation page was fetched.

## Gap summary

Nothing here ranks the tools. Sentences marked as probes or desk claims did not come from a model session.

mcp-language-server gives a model definition, references, hover and diagnostics from one TypeScript language server, but it takes a symbol name for definition and references, and on this checkout (only `.cts`, `.cjs` and `.js` files) the probe returned a "No Project" error and then "not found". It has one server per workspace, so a second worktree needs a second server and freshness is whatever that server has loaded. It returned no ADR relation, no stated degraded state, and its results are not documented as `file:line` citations. In the eight live sessions the model did not call it.

Serena offers symbol search, referencing symbols and symbol-level edits over a language-server backend, and its probe found the `.cts` function and its same-named bindings quickly with line numbers. Its references to the `.cts` function omitted the `.cjs` and `.js` callers, which is the `.cts` to `.cjs` emit mapping gap, and it has no ADR relation. Its default interface for a Claude Code session in this version is a REPL with two tools; the model called neither, and its design deliberately avoids `file:line` as an output form. It keeps its own data directory and, on first use, downloaded its own copy of a language server.

Aider's repo-map is orientation text and not a query tool: the 4,096-token map named 21 of 3,976 files, no `.cts` file and none of the question symbols, carried no callers, references, inheritance or ADR links, and had no marker for what the budget left out. The model ignored it in all eight sessions, and it added roughly 11,000 cache-creation tokens to each. The `file:line` form does not apply to it.

Codegraph answered the questions that name a symbol in one or two calls and abstained correctly when the symbol did not exist, but its caller listing for a `.cts` function omitted the `.cjs` and `.js` callers, it has no relation from code to an ADR number, and a second hop of callers fell back to shell search and ended partial. It keeps one index per worktree and warns when a result comes from another worktree's index, but no per-result degraded state was seen, and it cites `file:line` for definitions and direct callers only.

Claude Code's LSP plugin hands a language server's definition and references to the model inside Claude Code; the headless session started with the local plugin and listed the tool, but the model never called it, so what the server returns for `.cts` files was not observed. The desk limits are those of the language server: one server per workspace, no ADR relation, no stated degraded signal beyond the interactive Errors tab, and `file:line` only as far as the tool output happens to carry it.

Memtrace was reviewed at the desk only, because it is paid and its quota is exhausted; the one caveat that follows from the routing text is worktree freshness, since only one of its lookups takes a worktree argument. Nothing can be said about its ADR links, `.cts` mapping, degraded honesty or `file:line` form without a live run.

Taken together, and without ranking, no free tool in this scan met four needs of the eval's question categories on this corpus: callers and impact that cross the `.cts` to `.cjs` emit boundary (the two probes and the codegraph run each lost the `.cjs` and `.js` side), a link from code to ADR citations, a stated degraded state that tells the model what an answer left out, and per-worktree freshness that does not depend on which index is loaded. Where a tool returned results, line numbers came with Serena's and codegraph's listings; whether mcp-language-server or the LSP plugin return them was not observed. On the eight scan questions shell search alone answered seven fully and one partly in every installed row, so the case for a new tool rests on the cost of those searches (the impact question took 7 to 16 shell calls and 168,255 to 292,363 billable tokens, against 13,585 to 85,141 for each of the other questions) and on the needs above, not on the shell failing outright.
