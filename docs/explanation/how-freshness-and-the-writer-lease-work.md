# About how freshness and the writer lease work

gsd-atlas answers questions from an index that several processes may be using at once, while the code underneath changes. This page explains the choices behind that: why only one command creates an index, why one process at a time may write to it, how the index keeps up with edits, why housekeeping waits for quiet, and why every answer carries a citation and belongs to one worktree. It records reasons; the values and codes it mentions are in [the CLI reference](../reference/cli.md) and [the MCP reference](../reference/mcp.md), and the decisions are in [the design](../DESIGN.md) and the architecture decision records it links.

## Why does only `build` create an index?

A question should never change what it asks about. The first version of the host let any read tool create a store folder, take the writer lease and open a repository nobody had built. That had a second cost: while an agent's MCP server held the lease, the build the user was told to run in a terminal could no longer take it. The rule the host follows now is that a repository whose store is missing, holds nothing to read, or was written by an older schema is not opened by a question at all. The answer is `not_indexed`, it names the command to run, and it is produced before any store, lease or watcher exists ([the MCP contract record](../adr/13-mcp-contract.md), Amendment 2026-10-17).

The same reasoning covers a store that exists but holds nothing to read. Opening it as the leader would take the lease, and the build that the error message advertises would then fail. So a read request only looks, and the look creates nothing.

The status tool is treated like the others. The alternative was an `atlas_status` that answers "ok, empty" for a repository nobody built. The record rejects it: the published snapshot would need a nullable store, and an agent could not tell "indexed and empty" from "never built". The cost of the chosen rule is that the language tiers cannot be read before the first build.

Two things follow. A repository that was built is still written to by a read tool, but only inside the store folder: the lease files, the write-ahead log and the metrics database. And a question about an older commit needs no index at all, because it reads git objects and discards what it parses ([the worktree record](../adr/11-worktree-lifecycle.md), decision 3).

## What is the writer lease, and why do followers exist?

Several processes can be working on one repository's store: a command-line question, an agent's stdio server, a second agent's server. The store's durability rules call for one writer per store, with every query connection read-only and each file's facts changed in one transaction ([the SQLite store record](../adr/8-sqlite-store.md), decision 5), because SQLite's documented corruption causes are usage patterns ([the design](../DESIGN.md), A17). The fact store hands out its writer as a single lease ([the fact store record](../adr/7-fact-store-interface.md), decision 5), and [the tenant record](../adr/9-tenant-composition.md) makes the indexer the store's only writing client, which makes the single-writer rule structural. The lease is how the processes agree on which one it is.

The lease is a lock on a dedicated database file. The holder keeps it open for its whole life, and the operating system drops the lock when the holder dies, including when it is killed. That is why no code looks for stale leases: a process that cannot take the lock is simply a follower, and it tries again later. A small diagnostics file records the holder's process id, start time and version, and it is never used to decide who owns the lease ([the worktree record](../adr/11-worktree-lifecycle.md), Amendment 2026-10-16).

A follower is read-only and says so: its answers carry `degraded: follower`. It is not blind to your latest edits, though. For the paths named in a `fresh` argument it parses the files itself, builds an overlay in memory for that one request, merges it over the shared facts and answers from the merge, then drops it. It never asks the holder for anything and never writes. It also retries the lease on a jittered timer, so that when the holder ends one of the followers takes over and starts indexing.

The consequence is the awkward one. A terminal running the build command while an agent's server holds the lease cannot index; it answers `lease_held`. The host cannot hand a build to the process that holds the lease today, so the honest instruction, which the error text gives, is to end the agent session that started that process, build in a terminal, and start the agent again. The same limit explains why a command-line question asked while a server runs is answered as a follower.

Holding the lease is not permanent. A process that has had no request, and none in flight, for 30 minutes closes the repository and releases the lease, and the next request opens it again ([the tenant record](../adr/9-tenant-composition.md), Amendment 2026-10-17). A short command-line run holds the lease only while it runs, if it can take it at all.

## How does the index stay fresh?

The holder watches the working tree, and a watcher is only an accelerator. The native watcher reports a modification as a creation and an atomic-rename save as a deletion followed by a creation, so every event is read as "hash this path". Events can be lost (the watcher reports overflows and errors) and a platform can run out of watches. The index therefore does not trust them: a reconcile compares what the store believes with what git and the disk say, and repairs whatever the events missed. It runs at start-up, whenever git reports a branch switch or a change of worktrees, and on an idle interval of about ten minutes ([the worktree record](../adr/11-worktree-lifecycle.md), decision 6 and Amendment 2026-10-16). When the operating system cannot give the watches, the index falls back to scanning or to reconciling alone and says so in its status (`watch_fallback` for the latter) rather than pretending to be live.

Changes are coalesced before they are indexed, with a debounce of 100 ms and a longest wait of 500 ms. A file version is indexed once however many worktrees see it, because facts are keyed by the file's git blob id, computed with the filters git applies, which also lets any version be rebuilt from git ([the fact model record](../adr/6-fact-model.md), decision 5; [the design](../DESIGN.md), A24).

At start-up the holder reconciles before it can promise anything. The first request waits for that reconcile for at most 1500 ms. If it has not finished, the request is answered anyway, from the store, and marked `reconciling`, so a caller sees that the answer may lag the working tree instead of being held up by it.

The strongest guarantee is the one an agent asks for itself. After an edit, a request can name the paths it changed with `fresh`. The holder moves those paths to the front of its queue and the request waits up to 2000 ms for them, so that an agent that just wrote a file does not reason from its previous version ([the design](../DESIGN.md), A26). If the wait runs out, the answer says `fresh_timeout` and is given from what the store has.

Each answer states what it is as of. The watermark carries a sequence number that advances only after a commit to the worktree's index, and the list of paths the answer may not reflect yet. Reads report those paths and never wait for them: the store cannot wait on work it does not know about, so waiting belongs to the indexer and is requested with `fresh` ([the tenant record](../adr/9-tenant-composition.md), decisions 2 and 3).

## Why does compaction wait for idle?

An index that follows edits accumulates retired versions: every save leaves the previous version of a file behind until it is collected. In the measurement behind the design, 20,000 edits to a 10,000-file store grew it from 69 MB to 212 MB when old versions were kept, to 90 MB when they were collected, and to 80 MB when collection was followed by compaction. Housekeeping is therefore not optional. It sits lowest in the priority order, below interactive reads, fresh requests and change indexing, so that latency stays predictable under any load ([the design](../DESIGN.md), A28), and it runs when nobody is asking ([the worktree record](../adr/11-worktree-lifecycle.md), decision 5 and Evidence).

In practice the holder runs maintenance in slices of at most 200 ms, once a request has not arrived for 30 seconds. A request that arrives while a round is running makes the round stop at its next check, and the work resumes after the next quiet period. Only the lease holder does this, since only it may write.

There is one exception, and the record states it plainly. A full compaction rewrites the live data in a single synchronous step and cannot be sliced, so on a large store it is longer than a slice. It is therefore requested only after a collection that finished, and only when free pages exceed a quarter of the file or the space unused inside pages exceeds a third. A healthy store is never rewritten, and once a rewrite has started it is not interrupted ([the worktree record](../adr/11-worktree-lifecycle.md), Amendment 2026-10-17).

The size gate is built on the same idea. It asserts the size of the store after idle maintenance alone, measured before anyone asks for a full compaction, and compares it with a fresh build of the same content. A store that meets the bound only after a manual full compaction does not pass: the point is that nobody has to remember to tidy it. The earlier policy, which the gate measured at 1.3938 times a fresh build against a limit of 1.25, failed for exactly that reason.

## Why is every answer cited, and why does it belong to one worktree?

An answer that cannot be checked is a guess with better formatting. Every result carries a citation: a path, a position, whether the fact was extracted from the file or inferred by matching names, and a debug handle. Confidence is stated because grammar-level references are matched by name; an honest answer says `INFERRED` instead of passing a name match off as proof ([the fact model record](../adr/6-fact-model.md), decisions 3 and 4). A citation holds structure only. The matched source line travels separately, fenced with a nonce that differs for every response, because repository text is attacker-influenced and reaches a model's context. The fence lowers the risk of prompt injection and cannot remove it, which is why the tool descriptions say so ([the trust boundaries record](../adr/3-trust-boundaries.md), decision 4).

The index is shared by all worktrees of a repository, because by default it lives in the git common directory, so every worktree finds the same store and nothing is committed ([the design](../DESIGN.md), A4). What is shared is the part that does not depend on where you stand: facts about a single file are keyed by its content. What does depend on the worktree is how a reference resolves, since what a call reaches depends on the other files, configuration and dependencies of that worktree. An early draft keyed everything by file content and gave wrong answers across branches, so a reference is resolved per overlay, the map from paths to content that each worktree has, at read time from the facts of the files that worktree holds ([the fact model record](../adr/6-fact-model.md), Context; [the fact store record](../adr/7-fact-store-interface.md), Amendment 2026-10-15). The `repo` argument, or the working directory, selects the worktree whose overlay is used, and it is the listed worktree that contains the directory.

Questions about the past follow from the same choice. The store holds the current state of every live worktree and keeps a retired version only briefly, because git is already the history. A history question therefore reads the commit's objects, parses them into a throwaway store, answers and discards it, so it works on a repository nobody indexed and in a process that is not the holder ([the worktree record](../adr/11-worktree-lifecycle.md), decision 3).
