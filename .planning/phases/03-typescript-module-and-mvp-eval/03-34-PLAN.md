## Skill protocol (mandatory for every task of this plan)

The documentation is written with the user-level Claude skill `writing-docs-with-diataxis` (files: `~/.claude/skills/writing-docs-with-diataxis/SKILL.md` and `references/types.md`, `references/skills-repo.md`, `references/evidence.md`; expand `~` to the home directory). It has no scripts, templates or required arguments. Its inputs are the existing pages and the reader needs; its output is edited pages plus a short report of what changed and what remains.

**Invocation.** Before reading or writing any page under `docs/` or `README.md`, call the Skill tool with `skill: "writing-docs-with-diataxis"` (the exact name, no leading slash, no args). Do it once at the start of Task 1, and again at the start of a task if the session was restarted. If the Skill tool is unavailable or does not list that name, stop with a blocking-human report ("Precondition not met: skill writing-docs-with-diataxis"); do not write pages from memory or from the quotes below. After loading it, read `references/types.md` (the section of each type before writing that type, and its Checklists section before each commit) and `references/skills-repo.md` (the Publishing checklist and the README-as-front-door layout, because `skills/` ships and is documented here).

**What the skill requires** (quoted so this plan stands alone; the loaded skill governs if they differ):

- The compass. Ask two questions of every page and sentence: "Action or cognition? Does it inform what the user *does* (practical steps) or what they *know*?" and "Acquisition or application? Is the user at *study* or at *work*?" Action and study is a tutorial ("Can you teach me to...?"); action and work is a how-to guide ("How do I...?"); cognition and work is reference ("What is...?"); cognition and study is explanation ("Why...?").
- Write to the type. Tutorial: "a lesson in which the learner learns by doing something meaningful and achievable"; state the destination ("In this tutorial we will...", not "you will learn..."); a visible result at every step; narrate what to expect; minimise explanation (a clause and a link); stay concrete; ignore options and alternatives. How-to: "directions for an already-competent user with a real goal"; action only, no teaching, no digression; may fork ("If you want x, do y"); title "How to...". Reference: "neutral, austere, authoritative description of the machinery"; mirror the product's structure, standard patterns, short examples, warnings; "describe and only describe": link out for instruction and explanation. Explanation: discussion that deepens understanding (context, why, alternatives, opinion allowed); bounded by a topic; title "About..."; it does not absorb instruction or spec.
- Rules. Keep the types distinct and link between them; the commonest conflation is tutorial versus how-to (study versus work, not basic versus advanced); a list or table of facts is reference, what you would read away from the work is explanation; do not organise around product features; guide, not plan: no empty `tutorials/`, `how-to/`, `reference/`, `explanation/` skeletons; each page must stand as its type because readers do not move in order.
- Workflow when asked to "document X": "1. Read what exists; list each section/page with its quadrant (a quick table), using the compass rather than intuition. 2. Name mixed pages and unmet needs. Do not create empty pages for missing quadrants. 3. Run the loop on the highest-value piece first; make real edits, not just a plan. 4. For each moved or new piece, check: single type, language and title fit the type, links replace repeated explanation. 5. Report what changed and what remains, ranked." The loop is choose, assess, decide, do; publish each small step immediately (here: one docs-only commit per page).
- Publishing checklist for each page (skills-repo.md): exactly one quadrant; how-to title "How to <goal>"; explanation reads "About <topic>"; tutorial title states what will be built; tutorial steps were run start to finish and the final result matches; commands are copy-pasteable and use real paths; reference rows have one shape and nothing narrative; cross-links replace repeated explanation; the catalog entry per skill matches its `SKILL.md` description; no empty placeholder pages.

**Evidence the skill was used.** `03-DOCS-LEDGER.md` (created in Task 1, before the first page) holds the step-1 and step-2 results and the checklist per page; the plan summary holds the step-5 report (what changed, what remains, ranked) and the list of claims checked with their evidence.

## Documentation rules (apply to every task; tasks cite them as R1 to R9)

R1 Verify, never invent. Every command, flag, exit code, tool name, envelope field, error text, code and default is checked against the built CLI or a real test's expectation, or read from the code (read source through codegraph, R8). If it cannot be checked it is left out. Record each checked fact in the ledger's Facts table (statement, page, evidence as `file:line`, `run: <command>` or `test: <path>`).
R2 Examples. A ```json fence holds a complete, parseable example copied from a real run or a real test, with placeholders written as strings, and the line before the fence is a `verified-by` marker (see the truths). Abbreviated shapes use a plain `text` fence, never `json`. Interactive commands (`allow`, the prompts of `bug` and `diagnostics enable`) cannot be driven without a terminal: take their exact text from `--help` and from the tests that drive them (`src/cli/allow.test.ts`, `src/cli/diagnostics.test.ts`, the bug tests), name the test in the marker or the ledger, and never paraphrase a prompt into an invented one.
R3 Present state only. Describe what exists after plan 03-33. ## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| documentation to user action | A wrong instruction (an unsafe approval step, a command that does not exist, an invented prompt) leads a user to weaken their own security or to distrust the tool. |
| probe machine to published page | Output copied from a real run can carry paths, names or tokens of the machine that ran it. |
| documentation to claims | A page that states a result, a number or a status the repository does not back misleads readers. |
