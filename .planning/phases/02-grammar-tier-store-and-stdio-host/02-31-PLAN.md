<objective>
Fix WR-03: a failed takeover recovery or a failed `check` rebuild currently closes both database connections before it knows a replacement will open, swallows the error, and still reports leadership, so the Tenant starts an Indexer that writes into closed handles.

Phase goal (ROADMAP.md, quoted verbatim): "A developer can build a local fact index of gsd-core on macOS, Linux or Windows and ask cited, fresh, worktree-correct questions (find, refs, context, impact) through the CLI or a stateless stdio MCP server."

Purpose: STO-06 (detect and rebuild a damaged store) and STO-08 (takeover without a restart) must degrade honestly when the rebuild itself fails (D-14).
Output: a corrected `open.ts` and failure-injection tests.
</objective>

From open.ts: `openWithRecovery(env, deps)` (authority open that quarantines a damaged file and recreates it), `attemptOpen(env, authority)` (`ready` | `corrupt` | `older`), `noteRebuild(db, moved)`, `recoverAfterTakeover` (closes both handles, then `openWithRecovery`), `lifecycle.rebuild` (closes both handles, `quarantine`, `attemptOpen`, `noteRebuild`), `lifecycle.recovering` (writers refuse while true), `lifecycle.stopTakeover`, `startTakeover(lease, clock, range, onAcquired)` returning a cancel function.
From recovery.ts: `quarantine(dir, clock)` needs every connection closed first (Windows cannot rename an open file), `isDirty`, `runQuickCheck`, `clearDirty`. From lease.ts: `Lease.release()`, `tryAcquire()`.
Why the connections are closed first: a database file cannot be moved aside while a connection holds it open on Windows, so the "open the replacement first" order that the review suggested is not available for the quarantine step; the fix is restore-or-close afterwards.
</interfaces>
