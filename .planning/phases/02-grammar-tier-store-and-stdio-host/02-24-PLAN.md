    - "STO-09: `history` answers a code question about the repository as it was at a commit, from git alone, without writing to the real store: the commit is resolved with rev-parse, its tree is listed with ls-tree, the claimed-extension source files are read with ONE `git cat-file --batch` run, parsed by the pooled engine through the same module host as the Indexer, loaded into a throwaway Fact Store in a fresh temporary directory, answered by the same Query code, and then discarded; the real store directory's file names, sizes and contents are identical before and after (hashed in the acceptance test)."
    - "The history path never opens a Tenant: it needs only a Source Tree, the module host and an engine, so it works on an unindexed repository and in a follower process; it never fetches (a missing object in a shallow clone returns the error `commit_not_found` naming the revision) because every git spec pins lazy fetch and transport off."
    - "Only request forms the design supports are served: `history <tool> <name> --at <rev>` for tool find, refs, context or impact, with `--path <file>` restricting the tree to one file (the fast path, design budget two seconds for one file in gsd-core) and the whole-tree symbol form bounded by the approved history.maxFiles with a `history_truncated` warning and truncated true when the tree has more claimed files than the cap."
    - "Source Tree gains three methods used here: resolveCommit(rev) (null for an unknown revision; a rev starting with a dash or containing NUL is rejected before git), listTree(commit) returning entries {path, mode, type, oid} for blobs (symbolic links, submodules and non-blobs are skipped with diagnostics), and readMany(commit, paths) returning a map of path to bytes or null, implemented by a single cat-file batch run whose output is parsed binary-safely and whose per-blob size is capped at the source limit (oversize blobs are skipped with `source_too_large`)."
    - "Line text for history answers comes from the commit's own bytes held in memory by the history request (a text port backed by the blob map), never from the working tree, so citations show the historical lines; positions are those of the historical content."

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user-supplied revision strings to git | A revision is passed to git commands. |
| historical repository bytes to the parser | Old commits may hold hostile content like any file. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-----------|-----------------|
| T-02-88 | Elevation of Privilege | option injection or ref tricks through the revision string | high | mitigate | assertRevision rejects leading dashes, NUL and line breaks before git; the revision is passed as `REV^{commit}` after `--verify`, never as an option; paths in `COMMIT:PATH` lines are vetted; all specs are gitSpec-built with pinned config and environment. |
| T-02-89 | Tampering | writing to the real store or fetching from a remote | high | mitigate | The history path opens no Tenant and no real store; specs pin lazy fetch and transport off; tests hash the real store directory and assert no fetch-like command ran (prohibition above). |
| T-02-90 | Denial of Service | whole-tree history over a huge repository | medium | mitigate | The approved history.maxFiles cap with deterministic truncation and a warning; blob size cap; one git process for all blobs; governed by the interactive class. |
| T-02-91 | Information Disclosure | throwaway store left in the temp directory | low | mitigate | mkdtemp with owner-only mode on POSIX and removal in `finally` on every path, tested. |
