    1. Append a new section headed `## Addendum 2026-10-17 (gap closure)` after the last existing section. Do not edit any line above it. First line inside: `Addendum status: Proposed`.
    2. New keys, one table row each with columns Key, Proposed value, Consumed by plan, Basis:
       - `pool.loadTimeoutMs`, 30000, plan 02-39. Basis: WR-09. A grammar load (WASM instantiate plus query compile) has no deadline today and a language module can come from the repository, so one hung load occupies a parser worker forever. The value is far above a normal cold load (tens to a few hundred milliseconds on macOS; hosted Windows runners were measured 5 to 10 times slower in 02-VERIFICATION) and still bounds a hang.
       - `pool.terminateGraceMs`, 2000, plan 02-39. Basis: IN-06. The pool's hard deadline becomes the approved `indexer.parseTimeoutMs` (5000, unchanged, the engine's cooperative cut-off) plus this grace, 7000 ms, so an ordinary slow parse ends in the engine's own `parse_timeout` and the worker, with its loaded grammars, survives; terminating the worker is only the backstop for a stuck one.
       - `host.idleEvictMs`, 1800000, plan 02-41. Basis: WR-10. The Host closes a tenant, and a history module host, that has had no request and has none in flight for this long, which releases the repository's writer lease, three SQLite connections and the watcher. 30 minutes is three times the 10-minute idle Reconcile interval (D-13), so a session that is actually working never loses its leader.
       - `runner.defaultTimeoutMs`, 60000, plan 02-38. Basis: WR-07. The CommandRunner applies this limit to a `run()` spec that sets no `timeoutMs`, so a git process (or any other child) started by a caller that forgot one can no longer hang for ever. The value equals the approved `git.timeoutMs`; the runner default is the very 60 s that Phase 1 held back for a human decision (01-09), which is why it is listed here and not assumed. It never applies to `stream()` (long-lived children such as an MCP server in a test have no deadline) and an explicit `timeoutMs` always wins.
    3. Existing thresholds that become the idle loop's policy, with columns Key, Value, Lives in today, Note. Values are NOT changed by this plan:
       - `compact.fullFreeFraction`, 0.25 (free pages times four above the page count), `src/fact-store/lifecycle.ts` `worthVacuuming`, the rule of ADR 11 decision 5 ("free pages exceed 25 %").
       - `compact.fullUnusedFraction`, one third (unused bytes inside b-tree pages above a third of the file, read from `dbstat`), `src/fact-store/lifecycle.ts` `FRAGMENTED_FRACTION`, an internal bound of plan 02-18 chosen because a fresh build is about 26 percent empty inside; the margin is the hysteresis that keeps the idle loop from vacuuming every round.
    3b. Derived values, a table with columns Key, Value, Derivation (no free choice is involved, so these are recorded for the record and are in force without waiting for the reply):
       - `compact.checkpointBusyTimeoutMs`, 0. SQLite's busy timeout of 0 means "do not wait"; WR-04 requires exactly that for the truncating checkpoint, so it is a property, not a duration. The connection's previous value is restored afterwards.
       - `source.batchRecordAllowanceBytes`, 128. One record of `git cat-file --batch` is `<oid> <type> <size>` plus a line feed, then the body, then one line feed: at most 64 hex characters (the SHA-256 object format, the longest), 1 space, 6 characters (`commit`, the longest type word), 1 space, 20 digits (a 64-bit size), 1 line feed and 1 trailing line feed, which is 94 bytes, rounded up to 128. Plan 02-38 sets the output cap of the object batch to the selected blob sizes plus this allowance per record.
       - `source.batchCheckLineBytes`, computed per request: the output cap of `git cat-file --batch-check` is, for each input line, the larger of 94 bytes (a found record) and the length of the echoed spec plus 12 bytes (` missing` or ` ambiguous` plus a line feed), summed over the request. It is derived from the request itself, so it has no number to approve.
       - `compact.afterChurnFallback`, a rule and not a number: on a SQLite build without the `dbstat` table the idle loop requests the VACUUM after any collect that deleted files, instead of past the in-page threshold it cannot measure (plan 02-30). Both drivers were checked on 2026-10-17 and both have `dbstat`, so this is a safety net.
    4. Approved values reused without any change, as a bullet list: `git.timeoutMs` 60000 now applied to every Source Tree git spec (WR-07); `git.hashBatchTimeoutMs` 120000 for the batched object read; `gate.storeEditsRatio` 1.25 now asserted on the idle-only ratio (STO-05); `maintenance.sliceMs` 200 unchanged; `indexer.parseTimeoutMs` 5000 unchanged.
    5. Add a short `### Exception to maintenance.sliceMs` paragraph: a full VACUUM cannot be sliced, so the idle loop's full compaction (STO-05, D-16) is a pause longer than 200 ms on a large store. It runs only after a completed collect, only when `compact.fullFreeFraction` or `compact.fullUnusedFraction` is crossed, and the size gate (plan 02-37) prints its measured length so the owner can judge it against a real store.
    6. Add an empty `### Addendum approvals` heading to be filled by Task 2.
    7. If a guard hook refuses to let you write the file, do not work around it: stop and return a checkpoint that prints the tables in the message so the human can place them.
