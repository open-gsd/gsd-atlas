<objective>
Close the one blocker in 01-VERIFICATION.md (`gaps`, ROADMAP success criterion 4, FND-05 and FND-06) and the review item that shares its code path: new CR-01 (a filter driver whose name is not valid UTF-8 escapes neutralisation, and its repo-controlled `clean` command runs during `hash-object --stdin-paths`) and WR-01 (the builder and the gate disagree about which driver names are valid).

Phase goal (ROADMAP.md, quoted verbatim): "A developer can build and test the repo on macOS, Linux and Windows and run `gsd-atlas lang test` on a fixture language module end to end, with every module seam frozen behind an interface and a test double."

Root cause. `listFilterNames` decodes git's stdout with a non-fatal decoder, so an invalid byte becomes U+FFFD; `neutraliseFilters` puts that into `GIT_CONFIG_KEY_n`; Node encodes the environment string as UTF-8, producing EF BF BD; git compares bytes, so the neutralising key names a different driver than the configured one. Node cannot place arbitrary bytes in a child environment at all, so the environment channel cannot express such a name even with exact decoding. This is the same failure class as plan 01-19's CR-02: a name the builder cannot represent is a bypass. Reproduced by the verifier through `createRealRunner()` plus `createSourceTree()`, and re-reproduced by the planner on git 2.54.0: config bytes `[filter "a<0xFF>b"]` with a marker-writing `clean`, `.gitattributes` `a.txt filter=a<0xFF>b`, unprotected `hash-object --stdin-paths` wrote the marker, and so did a run whose `GIT_CONFIG_KEY_0` held U+FFFD in place of the byte.

Fix (the verifier's design, per D-10 and D-11): fail closed, because the only safe response to a name the channel cannot carry is to refuse the snapshot. One leaf module owns the rule (`filterNameProblem`); `listFilterNames` decodes with a fatal UTF-8 decoder and checks every listed name against the rule; `neutraliseFilters` refuses to emit what the gate refuses; `decide` validates channel keys with the same rule (WR-01). The existing hostile-repo tests are not touched.

Planner findings that shape the tasks (all observed, git 2.54.0, macOS arm64):
1. The invalid forms `61 ff 62`, `61 c3 28 62`, `61 ed a0 80 62` and the genuine `61 ef bf bd 62`, and a 1025-unit name, each fire their clean command when git hashes a file unprotected, so each gets a positive control. Valid UTF-8 names (café, an emoji) fire too and are carried correctly by the environment channel.
2. A name containing CR, tab or space cannot be referenced from `.gitattributes` (attribute values end at whitespace; an unprotected hash-object over `filter=a<CR>b` ran nothing), so those names have no positive control. Git does accept the same keys on the environment channel (exit 0), so tab and space names are representable.
3. CR stays refused. The gate's existing grammar already denies CR, loosening a security gate inside a gap-closure plan is the wrong direction, and refusing costs nothing real because such a driver cannot be triggered. What changes is the failure: a typed enumeration error naming the driver, instead of a denial at the hash step that says "not a first-party built-in".
4. `tsconfig.json` has `target: es2023`, so `String.prototype.isWellFormed` is not typed. The predicate detects unpaired surrogates itself.
5. A hostile repo's driver name is untrusted text and the error message may reach an agent: the message shows the name only through `JSON.stringify`, clipped, never raw (T-01-53).
